## 3. 健康巡检（稳定层#5）

**做什么**：每 15 分钟检查「会拖垮生产但 `/healthz` 未必发现」的信号——db 可解析、磁盘余量、备份新鲜度、服务端点可达。失败**非零退出**（经 journald 暴露），配了 `HEALTH_ALERT_CMD` 时还会调外部通知命令。

**看结果**：
```
journalctl -u ynzy-health-check.service -n 20 -o cat
```
输出形如（生产正常态）：
```
[health] {"ok":true,"checks":[
  {"name":"db","ok":true,"listings":77,"users":9,"sizeBytes":655896},
  {"name":"disk","ok":true,"freePct":30,"availKb":9197432,"minFreePct":10},
  {"name":"backup","ok":true,"latest":"db-backup-...Z.ygbak","ageHours":2},
  {"name":"service","ok":true,"httpCode":"200","port":3101}
],"failures":[]}
```

**手动触发一次**（oneshot，不影响主服务）：`systemctl start ynzy-health-check.service`，随后看上面的 journald。

**各 check 失败的含义与首步处置**：

| check | `ok:false` 意味着 | 先做什么 |
| --- | --- | --- |
| `db` | db.json 读不到 / 解析失败 / 缺 listings 数组 | 立即查 `server/data/db.json` 是否被截断或写坏；必要时从最新 .ygbak 恢复（见备份文档） |
| `disk` | 可用空间 < `DISK_MIN_FREE_PCT`（默认 10%） | `df -h /opt`；清理旧备份/日志；`BACKUP_RETENTION_DAYS` 是否过大 |
| `backup` | **已配置**备份目录但无新鲜备份 / backup 模块异常 | 查 `ynzy-offsite-backup`/`ynzy-db-backup` 是否在跑；`journalctl -u ynzy-offsite-backup`。注意：**未配置**备份目录才 `skipped`，配置了就 fail-loud，绝不假阳性 |
| `service` | `/healthz` 非 200 或不可达 | `systemctl status ynzy-miniapp`；`journalctl -u ynzy-miniapp -n 50`；查端口 3101 |

**告警凭据边界**：`HEALTH_ALERT_CMD` 的子进程只拿到系统必需变量 + 显式命名的 `HEALTH_ALERT_*` + 本次摘要（`buildAlertEnv` 白名单，默认拒绝）；**不会**继承 `BACKUP_ENCRYPTION_KEY`、`FEISHU_BACKUP_*` 等凭据。若要接 webhook 告警，另立专用 `HEALTH_ALERT_WEBHOOK`，**切勿**把备份/飞书凭据混命名成 `HEALTH_ALERT_*`。

## 4. 故障定位速查（现象 → 先看什么 → 命令）

| 现象 | 先看的信号 | 命令 / 位置 |
| --- | --- | --- |
| 接口 500 / 报错 | 请求链路日志 `[req]` | `journalctl -u ynzy-miniapp -n 100 \| grep '\[req\]'`（含请求 id、路径、状态、耗时） |
| 「刚发版后坏了」 | 当前版本 + 发布记录 | `cat server/version.json`；`node scripts/show-releases.js --last=5` |
| 聊天推荐卡「看详情/地图」为空 | 该房源 id 是否被日志脱敏破坏 | 查 `[req]` 里详情接口 rawFound；`listing.id` **不是** PII，不应被 scrub |
| 整体不可达 | 健康巡检 + 主服务 | 见 §3；`systemctl status ynzy-miniapp nginx` |
| 磁盘/备份异常 | 健康巡检 backup/disk 项 | 见 §3 表格 |
| 语音/ASR 不通 | Nginx `zf-api` 域 WebSocket 转发 | `nginx -t`；查 `zf-api-miniapp.conf` 的 `/mini/asr/realtime` |

**原则**：生产链路必须留下可复核日志或接口证据；不用 mock 冒充生产通过。日志里**不得**出现手机号 / 微信 / 房东电话 / 地址等 PII（已由 `scrubSensitiveText` 处理；`listing.id` 例外，不脱敏）。

## 5. 版本追溯与发布记录

| 文件 | 作用 | 备注 |
| --- | --- | --- |
| `server/version.json` | 当前运行版本（部署时写入） | gitignore，随部署生成 |
| `server/releases.jsonl` | 每次部署的历史（追加式） | gitignore；一行一条 JSON |

- 看当前版本：`cat server/version.json`
- 看最近发布：`node scripts/show-releases.js --last=10`（坏行自动跳过、文件缺失不崩）
- 记录一次发布：`node scripts/record-release.js --scope=full --verify=ok --by=<who> --note="<说明>"`（`deploy-ecs.ps1` 部署末尾会自动调用）

**"发布可追溯"闭环**：出问题时，先 `show-releases` 对齐最近改了什么、谁部署的、验证结果，再结合 `[req]` 日志定位。

## 6. 部署与回滚

### 6.1 staged 安全部署原则（任何生产变更都遵守）

1. **先备份**：改 db 或覆盖代码前，先有可恢复的备份。
2. **静态校验**：`node --check <改动的 .js>`（`.new` 扩展名无法 `--check`，用 `.js` 暂存名）。
3. **运行时验证**：新代码先在服务器跑一次（如 `node scripts/health-check.js`）确认结构正常。
4. **原子替换**：`scp` 到暂存名后 `mv` 就位；systemd 单元 `cp` 到 `/etc/systemd/system/` 后 `daemon-reload`。
5. **重启 + 自检**：重启后立即验证核心端点（`/healthz`、`/readyz`、以及**一个真实业务端点**，不要只测 healthz——历史教训：只测 healthz 漏掉了 domain.js 缺函数的 SEV1）。
6. **失败即回滚**：自检不过就从备份/上一版本回滚。
7. **记录发布**：`record-release.js` 落 `releases.jsonl`。

### 6.2 Windows 一键部署

`scripts/deploy-ecs.ps1`（PowerShell）：已内置 version.json 生成 + 断言、回滚备份、部署后自检（healthz / version / 详情接口非 500）、自动 `record-release`。
> 注意：`.ps1` 在 PowerShell 5.1（GBK）下中文会乱码，脚本正文用 ASCII 英文。

### 6.3 手动上线单个脚本 / 单元（以健康巡检为样例）

```bash
# 1) scp 到服务器
scp server/scripts/health-check.js root@114.55.168.97:/opt/ynzy-miniapp/server/scripts/
scp deploy/ynzy-health-check.service deploy/ynzy-health-check.timer root@114.55.168.97:/opt/ynzy-miniapp/deploy/
# 2) 服务器端校验 + 装单元（不重启主服务）
ssh root@114.55.168.97 '
  cd /opt/ynzy-miniapp/server && node --check scripts/health-check.js
  cp /opt/ynzy-miniapp/deploy/ynzy-health-check.{service,timer} /etc/systemd/system/
  systemctl daemon-reload
  systemctl enable --now ynzy-health-check.timer
  systemctl start ynzy-health-check.service   # 触发一次验证
  journalctl -u ynzy-health-check -n 6 -o cat
'
```

### 6.4 回滚

- **数据回滚**：从最新 `.ygbak` 恢复 db.json——**完整命令见 [`db-json-备份与恢复.md`](db-json-备份与恢复.md) 的「恢复命令」，本手册不重复。**
- **代码回滚**：`git` 回到上一已验证 commit 重新部署；或用 `deploy-ecs.ps1` 部署前留的回滚备份。
- **单元回滚**：`systemctl disable --now <timer>` 并删除 `/etc/systemd/system/<unit>`，`daemon-reload`。

## 7. 凭据边界（红线）

- `/etc/default/ynzy-backup`（chmod 600）持有 `BACKUP_ENCRYPTION_KEY`、`BACKUP_REMOTE_CMD`、`FEISHU_BACKUP_*` 等——**只在服务器，绝不入库 / 外发 / 进聊天**。
- 部署包与仓库**不含** `server/.env`、`server/certs`、`server/data`、真实 `.ygbak`。
- 加密口令丢失 = 所有备份无法解密；务必异地再保管一份。
- 健康巡检告警走白名单（§3），凭据不外泄给告警子进程。

> **待轮换（安全事项，值不写在此）**：root 登录密码、飞书备份 App Secret 此前在协作过程中暴露，**需尽快轮换**；轮换属凭据操作，须由用户执行、不作为自动任务推进。

## 8. 分佣配置与结算守恒（money）

平台分佣比例可后台配置，基数 = **成交总佣金**（`deal.landlordCommissionFen`，房东实付 / 签单时录入的总佣金），非月租。带看成交中介从中扣除上传人+平台后**净留其余**（默认 70%）。

| 房源类型 | 上传人 | 平台 | 带看成交中介净留 |
| --- | --- | --- | --- |
| 业主房源 | 20%（可配） | 10%（可配） | 70% |
| 二房东房源 | 20%（可配） | 10%（可配） | 70% |
| 公司房源 | 0 | 0 | 100%（带看全佣） |
| **自传自带**（成交人 == 上传人，任意类型） | — | 0（全免） | 100%、**不生成分佣记录** |

**后台配置**：admin-web「分佣配置」卡片可改 业主 / 二房东 的「上传人比例」与「平台比例」四个值（公司恒 0）。查看当前生效配置：`curl http://127.0.0.1:3101/mini/commission-config`。

**money 守恒双重防线（改配置 / 改数据前必须知道）**：
- **入口** `setCommissionConfig`：强制同类型 `上传人比例 + 平台比例 ≤ 100%`，超过 **400 拒绝**（后台保存前也同口径拦一次，不静默改用户配置）。
- **结算端** `confirmDeal`：确认签单前跑 `assertCommissionRuleConserved`——校验比例有限非负、`上传 + 平台 ≤ 100`、`rate == 上传 + 平台`；不符 **500 拒绝且不生成分佣记录**。即便 db 里已有历史脏配置、人工误改、或异常冻结快照绕过入口，也绝不真实超发。
- ⚠️ 因此**手工改 `db.commissionConfig` 或分佣相关数据时，务必保证同类型 上传+平台 ≤ 100**，否则确认签单会被结算端 fail-loud 挡下（不是静默容忍）。

**冻结快照**：签单时把当时分佣规则冻结进 `deal.commissionRule`，管理员确认**按冻结值结算、不重算**——房源在待确认期间被改（改类型 / 改成公司房源 / 上传人被提为管理员）不影响已签单分账。**改分佣配置只影响新签单，历史分佣记录不变。**

> 整包 / 全量部署前提醒：分佣是 money 级、需 Codex 审。确认部署包里没夹带他线**审查中未通过**的分佣改动（曾出现中间版被整包带上生产、缺守恒防线的漂移）。

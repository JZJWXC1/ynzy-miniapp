## 3. 健康巡检（稳定层#5）

**做什么**：每 15 分钟检查「会拖垮生产但 `/healthz` 未必发现」的信号——db 可解析、磁盘余量、备份新鲜度、服务端点可达，以及已启用的飞书 worker-v2 是否存在 `UNKNOWN/BLOCKED`、控制器错配或完整成功记录超过 18 小时健康窗口。失败**非零退出**（经 journald 暴露），配了 `HEALTH_ALERT_CMD` 时还会调外部通知命令。

**看结果**：
```
journalctl -u ynzy-health-check.service -n 20 -o cat
```
输出形如（生产正常态）：
```
[health] {"ok":true,"checks":[
  {"name":"db","ok":true,"listings":77,"users":9,"sizeBytes":655896},
  {"name":"disk","ok":true,"freePct":30,"availKb":9197432,"minFreePct":10},
  {"name":"backup","ok":true,"latest":"db-backup-...Z.ygbak","ageHours":2},
  {"name":"service","ok":true,"httpCode":"200","port":3101},
  {"name":"feishuSync","ok":true,"lastState":"succeeded","lastSuccessAgeMinutes":12,"maxAgeMinutes":90}
],"failures":[]}
```

**手动触发一次**（oneshot，不影响主服务）：`systemctl start ynzy-health-check.service`，随后看上面的 journald。

**各 check 失败的含义与首步处置**：

| check | `ok:false` 意味着 | 先做什么 |
| --- | --- | --- |
| `db` | db.json 读不到 / 解析失败 / 缺 listings 数组 | 立即查 `server/data/db.json` 是否被截断或写坏；必要时从最新 .ygbak 恢复（见备份文档） |
| `disk` | 可用空间 < `DISK_MIN_FREE_PCT`（默认 10%） | `df -h /opt`；清理旧备份/日志；`BACKUP_RETENTION_DAYS` 是否过大 |
| `backup` | **已配置**备份目录但无新鲜备份 / backup 模块异常 | 查 `ynzy-offsite-backup`/`ynzy-db-backup` 是否在跑；`journalctl -u ynzy-offsite-backup`。注意：**未配置**备份目录才 `skipped`，配置了就 fail-loud，绝不假阳性 |
| `service` | `/healthz` 非 200 或不可达 | `systemctl status ynzy-miniapp`；`journalctl -u ynzy-miniapp -n 50`；查端口 3101 |
| `feishuSync` | 自动同步控制器不是 worker-v2、存在未知/阻断任务、尚无成功记录，或成功记录超过 3 个周期 | 立即停止自动调度，按 §3.2 做只读对账；**不得**重跑原任务或删除状态 |

**告警凭据边界**：`HEALTH_ALERT_CMD` 的子进程只拿到系统必需变量 + 显式命名的 `HEALTH_ALERT_*` + 本次摘要（`buildAlertEnv` 白名单，默认拒绝）；**不会**继承 `BACKUP_ENCRYPTION_KEY`、`FEISHU_BACKUP_*` 等凭据。若要接 webhook 告警，另立专用 `HEALTH_ALERT_WEBHOOK`，**切勿**把备份/飞书凭据混命名成 `HEALTH_ALERT_*`。

### 3.1 告警到人：飞书群机器人（2026-07-10 起）

巡检/备份失败不再只进 journald——`server/scripts/send-feishu-alert.js`（零依赖）把失败推到飞书群。一个脚本同时接两条既有告警链：`HEALTH_ALERT_CMD`（巡检失败）与 `BACKUP_ALERT_CMD`（备份失败/自检失败/异地上传失败/备份过期/恢复演练失败）。

配置（`/etc/default/ynzy-backup`，chmod 600；webhook 属敏感配置，不进仓库/聊天/文档）：

```env
HEALTH_ALERT_WEBHOOK=<飞书群机器人 webhook 地址>
HEALTH_ALERT_SECRET=<可选：机器人开了「签名校验」才填>
HEALTH_ALERT_CMD="node /opt/ynzy-miniapp/server/scripts/send-feishu-alert.js"
BACKUP_ALERT_CMD="node /opt/ynzy-miniapp/server/scripts/send-feishu-alert.js"
```

> CMD 值带空格**必须加引号**：systemd `EnvironmentFile` 两种写法等价，但带空格不加引号时 `bash source` 会把值误当「临时变量+待执行命令」（验证命令会报 Permission denied）。2026-07-10 已按引号形态配置生产并实测：手动发送与「故意触发巡检失败→自动推群」两条链路均通。

创建机器人：目标飞书群 → 设置 → 群机器人 → 添加「自定义机器人」→ 复制 webhook（建议开启签名校验并同时配 `HEALTH_ALERT_SECRET`）。

验证（服务器上手动发一条测试消息，群里应收到「【寓你告警】…手动测试」）：

```bash
set -a; source /etc/default/ynzy-backup; set +a
node /opt/ynzy-miniapp/server/scripts/send-feishu-alert.js "手动测试：告警链路连通"
```

注意：脚本发送失败（缺 webhook/超时/飞书拒收）会非零退出并写 stderr，由调用方记入 journald——告警链自身故障不会打断巡检/备份主流程。契约由 `send-feishu-alert-v1-test.js` 锁定（已入 v1-final-audit 门禁）。

### 3.2 飞书公司房源 worker-v2

这一任务不再运行在常驻 API 进程的 `setInterval` 里。`ynzy-feishu-sync.timer` 显式按
`Asia/Shanghai` 时区在每天 `08:00 / 14:00 / 20:00` 唤醒 `ynzy-feishu-sync.service`；service 以 oneshot
方式执行 `server/scripts/run-feishu-sync-worker.js --schedule`，单次最长 5 小时。HTTP 后台只负责排队并立即
返回 202，worker 才负责源表读取、素材压缩、飞书 Drive、OSS、目标表、库存和首页 v2 十列快照的完整链路。

`FEISHU_SYNC_INTERVAL_MINUTES=30` 只用于 30 分钟内重复唤醒防重，不能改成 480；否则 08:00 与 14:00
可能被归入同一任务桶。`FEISHU_SYNC_HEALTH_MAX_AGE_MINUTES=1080` 独立表示 18 小时健康窗口，覆盖最长
12 小时日历间隔、单轮最多 5 小时运行时间及 1 小时运维余量。timer 不设 `OnBootSec`，并固定
`Persistent=false`，关机错过的日历点不补跑，避免每天出现第四轮；`AccuracySec=1s` 且无随机延迟。

#### 首次启用

1. 在服务器私有 `server/.env` 中保持 `FEISHU_AUTO_SYNC_ENABLED=false`，配置
   `FEISHU_SYNC_CONTROLLER_MODE=worker-v2`，确认 `DB_WRITE_LOCK` 未关闭；
   `FEISHU_APPROVED_SCHEMA_SHA256` 与 `FEISHU_APPROVED_RESOURCE_IDENTITY_SHA256` 先同时留空。
2. 员工源 Base 只授予应用读取权限；位置字典和业务目标 Base 才授予所需写权限。素材列必须通过
   `FEISHU_NOTE_MATERIAL_FIELD_ID=` 显式绑定真实 `field_id`，仓库和文档不保存默认值。
3. 安装发布包后确认 unit 已装载，但先不要开启自动写：

   ```bash
   systemctl daemon-reload
   systemctl status ynzy-feishu-sync.timer
   ```

4. 在管理后台连续建立两个独立“预演同步”任务（每次请求都只有 `{"dryRun":true}`，不得重跑旧
   runId）。接口返回 202 后，用后台状态面板或 `GET /admin/feishu-sync/status` 分别等待
   `dry-succeeded`。两次都要核对脱敏字段绑定、源/目标资源不重叠、`schemaSha256`、
   `resourceIdentitySha256`、`mirrorPlanSha256`、`contentPlanSha256`、素材数量，以及预演期间
   Base/Drive/OSS/数据库零写；若员工期间确实改表导致业务计划变化，等编辑稳定后重新建立一对预演，
   不能选择性忽略差异。
5. 把最新稳定预演对中人工核准的 `schemaSha256` 与 `resourceIdentitySha256` 分别写入服务器私有
   `FEISHU_APPROVED_SCHEMA_SHA256` 与 `FEISHU_APPROVED_RESOURCE_IDENTITY_SHA256`，重启主服务使
   管理状态读到新配置。再提交一次 `{"dryRun":false}`；worker 会重新形成并校验本轮全部摘要，客户端
   不能指定或复用 `runId`、时间、摘要、field binding 或 token。
6. 首轮状态必须是 `succeeded`，并同时对账目标表、飞书云盘、OSS、公开公司库存和
   `GET /mini/v2/company-sheet-snapshot` 的 `dataRowCount/columnCount/contentSha256`。确认小程序首页
   显示的十列首行就是业务数据而不是表头，抽查详情素材可播放。
7. 最后把 `FEISHU_AUTO_SYNC_ENABLED=true` 写入服务器私有环境，重启主服务并启用 timer：

   ```bash
   systemctl enable --now ynzy-feishu-sync.timer
   systemctl start ynzy-health-check.service
   systemctl list-timers --all | grep ynzy-feishu-sync
   journalctl -u ynzy-feishu-sync.service -n 30 -o cat
   ```

五个自动门缺一不可：总开关允许同步、自动开关显式开启、控制器精确为 `worker-v2`、schema SHA 与
资源身份 SHA 分别已批准、数据库跨进程写锁保持开启。timer 被唤醒不等于任务一定执行；未满足门禁时
worker 必须安全跳过或失败关闭。

#### 日常检查与故障处置

- 正常状态依次可能出现 `queued → dry-running → ready-to-apply → applying → committing → succeeded`；
  人工只预演以 `dry-succeeded` 结束。后台只显示脱敏摘要与计数，不显示 token、真实 field ID、路径或原始行。
- `ready-to-apply` 期间正式函数仍可执行 Base、Drive、OSS 的只读复验。长素材准备完成后会立即重读
  员工源、位置字典和目标表形成权威镜像计划 B；worker 必须先同步持久化 B，才允许后面的正式写阶段。
  B 可以吸收这段等待时间内非素材业务字段的最新事实，但 schema、资源身份、内容计划和“房源笔记”
  源字段不能漂移。只有首个真实写请求即将发出时，适配器才同步把任务推进到 `applying` 并先持久化
  写意图。可选空值和多选顺序已按业务语义归一；真正业务值、素材来源或批准边界变化仍会以
  `failed-before-write / MIRROR_*_CHANGED / NOTE_MATERIAL_SOURCE_FIELD_CHANGED` 结束，旧任务不得重跑。
- `succeeded + MATERIALS_PARTIAL_FAILURE` 表示房源表、库存和首页快照已经按受信计划发布，但有已知的
  单行素材延期。它不是完整成功：健康检查保持 `degraded`，`lastSuccessAt` 不刷新，并记录
  `lastWarningAt` 与真实失败数。保持 timer 运行，下一次任务会重新读取员工源并补传恢复的素材；同时
  按脱敏行状态核对该行是按计划保留旧受管素材还是清除旧受管素材，不要手工覆盖同键对象。
- `failed-before-write` 表示证据确认尚未进入外部写，可修正配置后建立**新任务**；不要重用旧 runId。
- 飞书目录/目标文件查询和 OSS HEAD/版本状态读取都属于写前检查；这类检查失败且创建、上传、PUT
  次数为 0 时不得升级成 `UNKNOWN`。只有真正发出创建、上传或 PUT 后无法完成确定性回读，才属于
  外部写状态未知。该边界由适配器的写派发回执锁定，禁止在调用适配器之前提前标记。
- `UNKNOWN` 表示外部写入可能已经发生但最终状态无法证明；`BLOCKED` 表示存在必须人工处置的冲突。
  两者都会阻断后续正式任务。立即设置 `FEISHU_AUTO_SYNC_ENABLED=false`、停止 timer，保留现场，只读核对
  目标 Base、Drive、OSS、数据库提交标记和公开快照。不得重跑原任务、删除状态、覆盖对象或用旧备份
  盲目恢复。只有确认外部与数据库事实并形成新的获批 schema/新任务后才能恢复。
- 对 v3 任务，若只读证据确认目标 Base 已经且仅仅落下该 exact run 的归档/流水前缀，其他目标、库存和
  首页均未推进，可在新代码发布且自动同步保持关闭时运行：

  ```bash
  node /opt/ynzy-miniapp/server/scripts/run-feishu-sync-worker.js \
    --continue-reconciled-partial <exact-run-id>
  ```

  入口会先硬校验 `FEISHU_AUTO_SYNC_ENABLED=false`；若自动开关已开启，会在创建 worker 和读取五表前失败，
  避免定时器立即拾取新任务。随后入口连续两次读取五表，用正式字段类型算法重建“去掉前缀”的写前快照并命中旧权威 B，同时校验当前
  业务数据库没有并发变化；它只把旧任务原子标记为 `reconciled-partial` 并排队一个全新任务，不会
  执行新任务。若证据中的归档、流水和当前主档增量均为 0，continuation 必须是 `dryRun=true` 的全新预演，
  且旧 `reconciled-partial` 继续作为持久正式写入屏障；人工或定时正式入队都必须返回
  `ZERO_WRITE_DRY_RUN_REQUIRED`；只有绑定同一旧任务、来源身份和对账证据的完整预演真正达到
  `dry-succeeded` 才解除屏障，预演失败不得放行正式任务，普通预演即使成功也不能解屏。只有确有归档/流水
  前缀时才允许排队正式 continuation。CLI 输出中的 `resolutionCode` 与 `dryRun` 必须按
  实际结果核对。仅在新任务仍是未经 recover/执行的原始 queued 记录时，重复调用才会校验旧 UNKNOWN 全量
  摘要、证据摘要、continuation 全量种子、scheduler 与 marker 后返回同一个新任务；一旦状态已推进或任一
  摘要、字段、数量、租约、blocker、业务快照或审计证据不一致，就失败关闭。随后必须单独执行该新任务，
  核对目标 Base、Drive/OSS、库存和首页快照；完整
  成功前不得开启 timer。该入口不能用于旧 v2 误分类、其他 UNKNOWN、批量解阻或跳过只读证据。
- 正式 continuation 若再次在首笔 Base 写请求后成为 `UNKNOWN`，仍可走同一个窄恢复门，但必须使用当前 exact
  runId；系统会分开保存本轮和父级的来源/证据摘要，并逐级核验唯一父子关系、原始排队种子、发起人、时间、
  请求键和证据，最多 32 层。孤儿、重复 ID、循环、跨任务借证或任一祖先漂移都会在读取飞书前失败关闭；不得
  删除继承字段、改库“拉平”链路或重跑任一旧入口。零写预演只有在同一完整祖先链仍受信时才能清除当前屏障。
  写前失败后的预演重试由屏障原子绑定当前授权重试 ID 与排队种子；旧预演、旧重试或绑定字段漂移都不得领取租约、
  联网或解屏。链路达到 32 层后若下一次续跑仍为 `UNKNOWN`，必须保持屏障并转人工只读事故复核，不再自动续建。
  worker 还会从任务记录反查未完成的零写屏障；`blockedRunId` 缺失、错指、屏障状态漂移或孤儿预演都必须停止，
  不得清空 scheduler 指针、改终态或删除父记录来恢复正式同步。
- 旧 worker-v2 若因“调用正式函数前就笼统落写意图”把明确的 `MIRROR_PLAN_CHANGED` 误记为 `UNKNOWN`，
  只能在 exact run 已完成 Base/Drive/OSS/数据库提交标记/公开快照五端只读对账后，使用代码提供的
  `resolveLegacyPrewriteDigestUnknown` 显式证据门处理。它要求旧版本、exact runId/error/SHA、一次尝试、
  无恢复、无真实写意图时间、无结果摘要、无提交标记且 blocker 精确指向该任务；任一条件不符都拒绝。
  禁止直接编辑 `db.json`、批量重解释旧 UNKNOWN 或把该入口用于新版本任务。
- 若最新 UNKNOWN 的外部写入结果无法逐项确认，且当前五表计划已因正常编辑而变化，旧 resolver 必须停止，
  不能要求员工把源表改回事故时字节，也不能把未知结果人工标成成功。保持 timer 与自动开关关闭，先在后台创建一条晚于 UNKNOWN
  的全新人工预演并等待 `dry-succeeded`；核对其五表/三类操作/首页表分项摘要、四个总摘要和素材数量后运行：

  ```bash
  node /opt/ynzy-miniapp/server/scripts/run-feishu-sync-worker.js \
    --create-current-convergence <blocked-run-id> <new-dry-run-id>
  node /opt/ynzy-miniapp/server/scripts/run-feishu-sync-worker.js --run <returned-new-run-id>
  ```

  第一条命令只原子创建唯一 v4 收敛任务，绝不顺带执行；第二条命令只运行回执中的新 runId，两条都不得重发旧
  UNKNOWN、旧 dry 或旧入口。收敛任务把旧 UNKNOWN、选择的 dry、五表分项证据、schema/resource/mirror/content
  与素材数量全部锁定，内部 dry、临写前预检和正式执行必须一致；内部 dry 有任何素材部分失败即停在写前。Base、Drive、OSS 只复用稳定身份且内容摘要一致的
  已完成结果，同身份异内容立即失败关闭，因此旧 UNKNOWN 即使曾部分写入，也只会补齐当前态仍缺少的结果。写前失败继续由旧 UNKNOWN 阻断；首写后未知由
  新任务阻断。写前租约过期也直接终结当前 run，必须以全新 dry 和全新 run 重建，不得自动重试原 run。只有数据库提交标记和独立 resolution marker 同事务落盘才解锁，旧 UNKNOWN 不改；marker 丢失或
  任何绑定漂移时 recover 自动重锁。成功后必须完成目标 Base、Drive/OSS、库存、首页 v2 快照和数据库五端对账，
  再按 §3.2 第 7 步开启每日三次 timer。
- 若 blocker 已是**正式写后的 V5 UNKNOWN**，停止使用上述 V5 收敛入口，也不要再创建更深的恢复任务。当前房源量较小时按以下一次性人工流程处理：

  1. 保持 `FEISHU_AUTO_SYNC_ENABLED=false`，执行 `systemctl disable --now ynzy-feishu-sync.timer`，确认同步 service、worker、活动租约和数据库写锁占用均为 0；旧 V3/V5 记录、marker 与 blocker 不得手改。
  2. 人工只读核对 source/location/mini/rented/history 五表，并在飞书网页端修正少量明确差异。此步骤不是代码自动修表，任何记录归属不清都应停下人工确认。
  3. 通过现有后台“预演”操作顺序创建并完成两条全新的 manual dry，记录两个 runId。两条都须为 `dry-succeeded`，晚于失败 V5，五表、schema/resource、mirror/component/content、素材数量和本地预演汇总一致，且 main/archive/history/baselineMarker 四类操作均为 `count=0 + 空操作摘要`。
  4. 在服务器项目目录生成只读批准清单：

     ```bash
     node scripts/run-feishu-sync-worker.js \
       --plan-manual-noop-resolution <failed-v5-run-id> <dry1-run-id> <dry2-run-id>
     ```

     该命令不得联网或写库。人工只核对脱敏任务号、五表计数/摘要、四类零操作和有效期，不把记录正文、手机号或 token 复制到批准记录。
  5. 在第二条 dry 完成后 30 分钟内，用上一步原样输出的 `approvalSha256` 执行本地原子解屏：

     ```bash
     node scripts/run-feishu-sync-worker.js \
       --apply-manual-noop-resolution <failed-v5-run-id> <dry1-run-id> <dry2-run-id> <approval-sha256>
     ```

     预期回执为 `blockerCleared=true`、`externalWrites=0`。旧 UNKNOWN 不会改成成功；数据库事务失败、业务快照变化、证据过期或摘要不一致时必须完整回滚并重新做两次 dry。
  6. 继续保持 auto/timer 关闭，创建一条全新的普通 manual formal。只有该任务 `succeeded`，且目标五表仍无剩余差异、Drive/OSS、本地 listings、首页 v2 与数据库 commit marker 五端一致后，才把“同步恢复”记为完成。
  7. 恢复每日 `08:00 / 14:00 / 20:00` timer 属于另一次生产授权；本地解屏成功本身不授权启用。

  当前员工源仍是过渡期权威入口。以后改为直接维护小程序表时，必须先发布显式的目标表直管模式并验证员工源读取与目标 Base 回写均为 0；不能只停员工源或互换 token。
- 首页 v2 接口网络失败、5xx、坏摘要或坏列必须按故障处理；只有 HTTP 404 表示服务器仍是旧版并允许
  客户端临时回退 v1。不要通过改成“所有错误都回退”掩盖首页行列错位。

#### 停用与回滚

普通停用先把 `FEISHU_AUTO_SYNC_ENABLED=false` 写入服务器私有环境并重启主服务，再执行：

```bash
systemctl disable --now ynzy-feishu-sync.timer
systemctl status ynzy-feishu-sync.service
```

紧急止写还要设置 `FEISHU_SYNC_ENABLED=false`。回滚代码前必须确认没有 `queued/dry-running/applying/
committing` 任务，保留 `feishuSyncRuns`、scheduler 和 commit marker 作为审计事实；禁止通过恢复旧
`db.json` 或清空这些状态来“解除阻断”。代码和 unit 回滚后仍先关闭自动同步，跑一次新版本 dry-run、
核对生产 `listings` 总数和首页 v2 快照，再决定是否重新启用。

## 4. 故障定位速查（现象 → 先看什么 → 命令）

| 现象 | 先看的信号 | 命令 / 位置 |
| --- | --- | --- |
| 接口 500 / 报错 | 请求链路日志 `[req]` | `journalctl -u ynzy-miniapp -n 100 \| grep '\[req\]'`（含请求 id、路径、状态、耗时） |
| 「刚发版后坏了」 | 当前版本 + 发布记录 | `cat server/version.json`；`node scripts/show-releases.js --last=5` |
| 聊天推荐卡「看详情/地图」为空 | 该房源 id 是否被日志脱敏破坏 | 查 `[req]` 里详情接口 rawFound；`listing.id` **不是** PII，不应被 scrub |
| 整体不可达 | 健康巡检 + 主服务 | 见 §3；`systemctl status ynzy-miniapp nginx` |
| 磁盘/备份异常 | 健康巡检 backup/disk 项 | 见 §3 表格 |
| 语音/ASR 不通 | Nginx `zf-api` 域 WebSocket 转发 | `nginx -t`；查 `zf-api-miniapp.conf` 的 `/mini/asr/realtime` |

**原则**：生产链路必须留下可复核日志或接口证据；不用 mock 冒充生产通过。日志里**不得**出现手机号 / 微信 / 房东电话 / 地址等 PII（已由 `scrubSensitiveText` 处理；`listing.id` 例外，不脱敏）。

## 6. 部署与回滚

### 6.1 staged 安全部署原则（任何生产变更都遵守）

1. **先备份**：改 db 或覆盖代码前，先有可恢复的备份。
2. **静态校验**：`node --check <改动的 .js>`（`.new` 扩展名无法 `--check`，用 `.js` 暂存名）。
3. **运行时验证**：新代码先在服务器跑一次（如 `node scripts/health-check.js`）确认结构正常。
4. **原子替换**：`scp` 到暂存名后 `mv` 就位；systemd 单元 `cp` 到 `/etc/systemd/system/` 后 `daemon-reload`。
5. **重启 + 自检**：重启后立即验证核心端点（`/healthz`、`/readyz`、以及**一个真实业务端点**，不要只测 healthz——历史教训：只测 healthz 漏掉了 domain.js 缺函数的 SEV1）。
6. **失败即回滚**：自检不过就从备份/上一版本回滚。
7. **记录发布**：`record-release.js` 落 `releases.jsonl`。

### 6.2 Windows 一键部署

`scripts/deploy-ecs.ps1`（PowerShell）：已内置 version.json 生成 + 断言、回滚备份、部署后自检（healthz / version / 详情接口非 500）、自动 `record-release`。
> 注意：`.ps1` 在 PowerShell 5.1（GBK）下中文会乱码，脚本正文用 ASCII 英文。

### 6.3 手动上线单个脚本 / 单元（以健康巡检为样例）

```bash
# 1) scp 到服务器
scp server/scripts/health-check.js root@114.55.168.97:/opt/ynzy-miniapp/server/scripts/
scp deploy/ynzy-health-check.service deploy/ynzy-health-check.timer root@114.55.168.97:/opt/ynzy-miniapp/deploy/
# 2) 服务器端校验 + 装单元（不重启主服务）
ssh root@114.55.168.97 '
  cd /opt/ynzy-miniapp/server && node --check scripts/health-check.js
  cp /opt/ynzy-miniapp/deploy/ynzy-health-check.{service,timer} /etc/systemd/system/
  systemctl daemon-reload
  systemctl enable --now ynzy-health-check.timer
  systemctl start ynzy-health-check.service   # 触发一次验证
  journalctl -u ynzy-health-check -n 6 -o cat
'
```

### 6.4 回滚

- **数据回滚**：从最新 `.ygbak` 恢复 db.json——**完整命令见 [`db-json-备份与恢复.md`](db-json-备份与恢复.md) 的「恢复命令」，本手册不重复。**
- **代码回滚**：`git` 回到上一已验证 commit 重新部署；或用 `deploy-ecs.ps1` 部署前留的回滚备份。
- **单元回滚**：`systemctl disable --now <timer>` 并删除 `/etc/systemd/system/<unit>`，`daemon-reload`。

## 7. 凭据边界（红线）

- `/etc/default/ynzy-backup`（chmod 600）持有 `BACKUP_ENCRYPTION_KEY`、`BACKUP_REMOTE_CMD`、`FEISHU_BACKUP_*` 等——**只在服务器，绝不入库 / 外发 / 进聊天**。
- 部署包与仓库**不含** `server/.env`、`server/certs`、`server/data`、真实 `.ygbak`。
- 加密口令丢失 = 所有备份无法解密；务必异地再保管一份。
- 健康巡检告警走白名单（§3），凭据不外泄给告警子进程。

> **待轮换（安全事项，值不写在此）**：root 登录密码、飞书备份 App Secret 此前在协作过程中暴露，**需尽快轮换**；轮换属凭据操作，须由用户执行、不作为自动任务推进。

## 8. 分佣配置与结算守恒（money）

平台分佣比例可后台配置，基数 = **成交总佣金**（`deal.landlordCommissionFen`，房东实付 / 签单时录入的总佣金），非月租。带看成交中介从中扣除上传人+平台后**净留其余**（默认 70%）。

| 房源类型 | 上传人 | 平台 | 带看成交中介净留 |
| --- | --- | --- | --- |
| 业主房源 | 20%（可配） | 10%（可配） | 70% |
| 二房东房源 | 20%（可配） | 10%（可配） | 70% |
| 公司房源 | 0 | 0 | 100%（带看全佣） |
| **自传自带**（成交人 == 上传人，任意类型） | — | 0（全免） | 100%、**不生成分佣记录** |

**后台配置**：admin-web「分佣配置」卡片可改 业主 / 二房东 的「上传人比例」与「平台比例」四个值（公司恒 0）。查看当前生效配置：`curl http://127.0.0.1:3101/mini/commission-config`。

**money 守恒双重防线（改配置 / 改数据前必须知道）**：
- **入口** `setCommissionConfig`：强制同类型 `上传人比例 + 平台比例 ≤ 100%`，超过 **400 拒绝**（后台保存前也同口径拦一次，不静默改用户配置）。
- **结算端** `confirmDeal`：确认签单前跑 `assertCommissionRuleConserved`——校验比例有限非负、`上传 + 平台 ≤ 100`、`rate == 上传 + 平台`；不符 **500 拒绝且不生成分佣记录**。即便 db 里已有历史脏配置、人工误改、或异常冻结快照绕过入口，也绝不真实超发。
- ⚠️ 因此**手工改 `db.commissionConfig` 或分佣相关数据时，务必保证同类型 上传+平台 ≤ 100**，否则确认签单会被结算端 fail-loud 挡下（不是静默容忍）。

**冻结快照**：签单时把当时分佣规则冻结进 `deal.commissionRule`，管理员确认**按冻结值结算、不重算**——房源在待确认期间被改（改类型 / 改成公司房源 / 上传人被提为管理员）不影响已签单分账。**改分佣配置只影响新签单，历史分佣记录不变。**

> 整包 / 全量部署前提醒：分佣是 money 级、需 Codex 审。确认部署包里没夹带他线**审查中未通过**的分佣改动（曾出现中间版被整包带上生产、缺守恒防线的漂移）。

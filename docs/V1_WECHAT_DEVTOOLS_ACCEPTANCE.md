# 第一版微信开发者工具验收清单

本文档用于第一版正式验收前在微信开发者工具中逐项核对，避免验收跑偏。第一版只面向中介使用，核心闭环是：找房、房源、地图、报备、签单、管理员确认分佣。

## 验收前准备

1. 确认当前分支是第一版验收分支，并已拉取最新代码。
2. 在项目根目录执行轻量检查：

```bash
node server/scripts/v1-acceptance-check.js
```

3. 如需补充后端契约回归，可继续执行：

```bash
node server/scripts/map-v1-test.js
node server/scripts/assistant-v1-test.js
node server/scripts/backend-contract-v1-test.js
```

4. 打开微信开发者工具，导入当前小程序目录。
5. 确认环境配置可访问测试后端，且测试数据至少包含：
   - 1 套有视频、有效、已确认小区坐标的房源。
   - 1 套有视频、有效、但无可靠坐标的房源。
   - 1 套已失效或 7 天未维护的房源。
   - 1 个普通中介账号。
   - 1 个管理员账号或可访问管理后台的测试账号。

## 一、底部导航

验收目标：第一版底部导航固定为找房、房源、地图、我的。

步骤：

1. 编译小程序并进入首页。
2. 检查底部导航只显示 4 个入口。
3. 逐个点击找房、房源、地图、我的，确认都能打开对应页面。
4. 检查底部导航中不能出现房源群、积分、充值、换群、微信支付。

通过标准：

- 底部导航顺序固定为：找房、房源、地图、我的。
- 没有租客端、房东端或其他角色入口。
- 没有房源群、积分、充值、换群、微信支付可见入口。

## 二、上传房源

验收目标：普通房源上传必须带视频，第一版不允许用图片替代视频。

步骤：

1. 使用中介账号进入我的。
2. 点击上传房源。
3. 不选择视频，填写其他必填字段后提交。
4. 选择视频后再次提交。
5. 如有编辑历史无视频房源的场景，确认保存前会要求补传视频。

通过标准：

- 未上传视频时提交被拦截，并提示房源视频必填。
- 只能选择视频素材，不能选择图片冒充房源视频。
- 成功提交后房源带有视频标识。
- 前端不能让用户修改上传人、分佣比例等服务端固定字段。

## 三、找房助手

验收目标：找房助手先识别需求，字段不足时追问，字段足够时展示确认字段，确认后再匹配房源。

步骤：

1. 进入找房对话或找房助手入口。
2. 输入不完整需求，例如“必须有阳台”。
3. 确认助手只追问一个关键问题，不直接推荐房源。
4. 输入完整需求，例如“滨江四千以内两室，必须有燃气”。
5. 检查确认字段是否包含预算、位置、户型、入住时间、通勤、偏好。
6. 点击确认后查看匹配结果。
7. 从匹配结果点击看详情。
8. 从匹配结果点击地图查看。

通过标准：

- 识别阶段不返回房源卡片。
- 信息不足时只追问，不强行匹配。
- 信息足够时先展示字段确认。
- 确认后才返回真实有效房源。
- 地图查看会带筛选条件进入地图页。

## 四、房源列表与详情

验收目标：前台只展示有效且有视频的房源，不展示失效资产和敏感信息。

步骤：

1. 进入房源列表。
2. 使用区域、租金、户型等筛选条件。
3. 打开任意房源详情。
4. 检查详情页视频区域、房源基础信息、报备签单入口。
5. 检查失效房源是否仍从前台隐藏。

通过标准：

- 前台列表只展示有效房源。
- 无视频历史房源不进入前台列表、匹配结果和详情。
- 详情页不直接展示楼栋、单元、房号、完整地址、房东电话、上传人电话。
- 敏感信息查看需要明确操作并留下足迹。

## 五、地图找房

验收目标：地图是第一版核心功能，只展示真实且经过确认的小区坐标，并显示筛选后的套数。

步骤：

1. 进入地图页。
2. 检查地图上是否出现小区点位。
3. 点击小区点位，查看小区名称、租金区间、套数和房源摘要。
4. 使用租金、户型、租赁方式、房源类型筛选。
5. 检查地图点和套数是否随筛选变化。
6. 从找房助手带条件跳转地图，检查地图按条件筛选。
7. 检查无可靠坐标房源是否没有进入地图。

通过标准：

- 地图只展示小区位置，不展示楼栋、单元、房号、完整地址和房东电话。
- 小区点必须来自可靠坐标或管理员确认坐标。
- 随机坐标、散列坐标、区域估算坐标、默认中心点、旧偏移坐标不能进入地图。
- 无可靠坐标房源可以在普通列表出现，但不能在地图出现。
- 小区点展示的是筛选后的有效套数。

## 六、报备

验收目标：第一版报备保持简单，客户称呼可选，客户手机号必填。

步骤：

1. 打开一套有效房源详情。
2. 点击先报备客户，再从报备发起签单。
3. 不填写客户手机号，提交报备。
4. 填写客户手机号，客户称呼留空，提交报备。
5. 再填写客户称呼和手机号，提交报备。

通过标准：

- 客户手机号为空时不能提交。
- 客户称呼可以为空。
- 报备成功后进入签单提交流程。
- 客户手机号不得在前台日志或提示中完整输出。

## 七、签单

验收目标：签单只能从报备记录发起，字段仅包含成交月租、房东实际支付佣金、可选备注。

步骤：

1. 完成一条报备。
2. 进入签单弹窗。
3. 不填写成交月租，提交。
4. 不填写房东实际支付佣金，提交。
5. 填写成交月租、房东实际支付佣金，可选填写备注后提交。
6. 尝试从旧的直接房源签单入口或接口绕过报备。

通过标准：

- 未完成报备不能提交签单。
- 成交月租必填。
- 房东实际支付佣金必填。
- 备注可选。
- 前端不提交也不允许修改 brokerId、uploaderId、commissionRate。
- 旧的直接房源签单路径必须被后端拒绝。

## 八、后台确认与分佣

验收目标：管理员确认签单后才生成正式分佣记录，上传人分佣固定为房东实际支付佣金的 20%。

步骤：

1. 用中介账号提交签单。
2. 在管理员后台查看待确认签单。
3. 确认签单前检查分佣记录。
4. 管理员确认签单。
5. 再次查看分佣记录。

通过标准：

- 管理员确认前不生成正式分佣记录。
- 管理员确认后生成正式分佣记录。
- 上传人分佣 = 房东实际支付佣金 x 20%。
- 金额按分存储和计算，展示时再格式化为元。
- 客户端提交的 brokerId、uploaderId、commissionRate 不影响最终归属和比例。

## 九、房态 3/5/7 天规则

验收目标：房态规则固定为第 3 天提醒、第 5 天再次提醒、第 7 天未更新自动失效。

步骤：

1. 准备不同最后维护时间的测试房源。
2. 检查第 3 天房源是否进入提醒。
3. 检查第 5 天房源是否进入再次提醒。
4. 检查第 7 天未更新房源是否自动失效。
5. 检查失效房源是否从前台列表、匹配、地图隐藏。
6. 在后台资产池确认失效房源仍保留。

通过标准：

- 第 3 天提醒。
- 第 5 天再次提醒。
- 第 7 天未更新自动失效。
- 前台只展示有效房源。
- 失效房源保留在后台资产池。

## 十、敏感信息与密钥

验收目标：不在日志和前台输出完整敏感信息，不把密钥写入仓库。

步骤：

1. 在房源列表、找房结果、地图、详情初始态检查房源信息。
2. 检查敏感信息查看后的足迹记录。
3. 检查后端日志和前端控制台输出。
4. 检查仓库中没有提交 `.env`、私钥、证书、AccessKey 等密钥文件。

通过标准：

- 不直接展示完整客户手机号、房东电话、微信号、身份证信息。
- 不直接展示具体楼栋、单元、房号、完整地址。
- LLM 或找房助手提示词不携带完整敏感原文。
- 仓库不包含密钥，生产密钥只来自环境变量或部署平台配置。

## 十一、第一版隐藏入口

验收目标：历史代码可以保留，但第一版前台入口必须隐藏。

步骤：

1. 检查底部导航。
2. 检查我的页工作台、提醒、统计。
3. 检查首页和房源详情的可点击入口。
4. 搜索是否有公开跳转到房源群、积分、充值、换群、微信支付。

通过标准：

- 房源群、积分、充值、换群、微信支付不作为第一版可见入口。
- 历史后端代码可以保留，但不能从第一版前台流程进入。
- 不能新增租客端、房东端或其他角色流程。

## 一票否决项

以下任一项出现时，不建议通过第一版验收：

- 底部导航不是找房、房源、地图、我的。
- 上传房源可以不传视频。
- 找房助手跳过字段确认直接推荐。
- 地图出现无可靠坐标、默认中心、区域估算或随机坐标房源。
- 地图展示楼栋、单元、房号、完整地址或房东电话。
- 报备客户手机号非必填。
- 签单可以绕过报备。
- 管理员确认前生成正式分佣。
- 上传人分佣不是房东实际支付佣金的 20%。
- 前台出现房源群、积分、充值、换群、微信支付入口。
- 日志或前台输出完整客户手机号、房东电话、微信号、身份证信息。
- 仓库包含密钥。

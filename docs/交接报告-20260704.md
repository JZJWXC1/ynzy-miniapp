# 交接报告 2026-07-04

## 1. 项目定位与当前架构

一句话定位：寓你住一起第一版是面向内部中介的杭州租房小程序，用公司同步房源与合作房源帮助中介找房、受控查看联系方式、拨号并沉淀审计留痕；新增报备与签单当前暂停，历史数据只读保留。

当前架构：

- 小程序端：微信小程序，底部导航固定为找房、房源、地图、我的；首页含公司房源快照与 `Yooni小助手`。
- Node 后端：`server/src/index.js` 提供 `/mini/*`、`/admin/*`、ASR/LLM、飞书同步、OSS 策略、报备签单等接口。
- JSON 库：运行数据存放在 `server/data/db.json`，由 `server/src/db.js` 读写；生产通过 systemd timer 定时备份。
- OSS：视频上传和源文件存储走阿里云 OSS，后端只持久化受控 `videoKey` 或可还原受控对象键的兼容源 URL；小程序公开 DTO 只拿 API 域不透明媒体能力地址，不把视频文件、对象键或 OSS 签名参数写入 JSON 响应。
- 飞书同步：公司房源从只读员工源表和素材库同步到目标 Base、本地 `listings`、飞书云盘与 OSS；后台只负责 HTTP 202 排队，独立 worker-v2 持久化执行，systemd 按北京时间每日 08:00、14:00、20:00 检查自动任务。
- LLM 助手：小程序助手和语音链路走后端，游客与登录中介都可匹配全部当前有效的公司、业主、二房东房源；游客提示词和卡片只使用公开字段白名单。
- 管理后台：`admin-web` 使用同一个 Node 服务托管，提供房源、审核、飞书同步、坐标修正、LLM 配置、导出等管理能力。

## 2. 业务规则现行版

### 2.1 分佣矩阵

当前报备/签单写入暂停；详情页佣金明细和历史恢复计算都只由服务端产生，客户端提交的 `brokerId`、`uploaderId`、维护人、比例、金额或同名字段不可影响结果。

| 房源情形 | 房东总佣金 | 带看人 | 房源维护人 | 平台 |
| --- | ---: | ---: | ---: | ---: |
| 公司房源 | 房源登记的月租占比 | 总佣金的 100% | 0% | 0% |
| 二房东/业主房源 | 房源登记的月租占比，缺失存量迁移为 50% | 总佣金的 70% | 总佣金的 20% | 总佣金的 10% |

例如房东总佣金为月租 50%，二房东/业主房源对应带看人 35%、维护人 10%、平台 5%（均为月租占比）。若未来显式恢复写入，服务端按成交月租与房源佣金比例自动计算金额并冻结当时身份与拆分快照；当前页面不提供新增报备或签单入口。

### 2.2 视频要求

- 公司房源免视频，允许无视频进入公司房源列表和详情；无视频时列表/详情显示明确空态且不展示保存、转发按钮。飞书同步本轮缺素材或转存失败时仍标记 `missingVideoMaterial=true`；只有更新前明确持续在架、更新前后完整物理房源键一致，且已有可解析为受控对象键的视频时，才保留上次视频并另标“沿用上次视频·素材待核”。新建无素材房源、否定/成交/历史终态、物理键变化，以及曾下架/过期后重新出现但无本轮素材的房源，均不沿用旧视频。
- 飞书员工源、目标 Base、库存、首页 v2 快照和房源笔记素材现由持久化 worker-v2 统一处理。单行已知素材故障会形成受信延期计划：正常房源和首页继续发布，失败行按同链接、同物理房间、同媒体状态决定保留或清除旧受管素材，并在下一次计划任务重试；任务显示 `MATERIALS_PARTIAL_FAILURE` 且健康状态降级，不冒充完整成功。只有真实创建/上传/PUT 已派发但回读不明才进入 `UNKNOWN`；纯读取预检失败不会误封存整批。
- 二房东房源、业主房源必须带真实视频，`videoUrl` 或 `videoKey` 至少有一个。
- 视频本体不写入 `db.json`。公开播放地址为默认 6 小时的 API 域不透明能力 URL；每次 `GET/HEAD/Range` 都重验房态，再由后端按需短签 OSS 并流式转发。视频首帧封面的客户端 HEAD 在 API 层保持无正文语义，内部专门转换为一次 OSS `video/snapshot` GET，读取合法图片响应头后立即销毁上游响应，规避生产截帧链对 HEAD 返回 502；普通视频/图片 HEAD 仍原样走上游 HEAD。

### 2.3 可见性边界

- 游客可看公司房源既有公开字段：首页快照、列表、详情都公开房号、完整地址、看房方式密码和备注；联系方式仅限服务器配置的统一号码，飞书或房源原文中的手机号、座机、邮箱、社交账号和私聊链接不属于公开字段。
- 游客可看全部当前有效的公司、业主、二房东房源卡片、公开详情和合作房源视频；公开位置只到城市、区域、板块和小区，不影响游客知道这个小区有房或把视频推荐给租客。
- 业主、二房东房源的楼栋、单元、房号、完整地址、房东电话、看房方式、钥匙位置、密码和敏感备注必须由有效账号二次确认，经查看额度和服务端足迹后单独返回；不再绑定需求单或用途。
- 列表、地图、助手和附近推荐的“全部”是三类来源并集，三个来源标签严格互斥。来源、身份、维护人、权限和敏感投影只由服务端判定，客户端同名字段不能改变结果。
- 游客可直接播放、转发和保存合作房源视频；匿名客户端不写视频转发足迹。收藏、拨号、带看、敏感查看及其他业务写操作仍要求登录。
- 上传、我的、需求单、分佣、足迹、视频上传策略等活动接口强制登录；历史报备/签单查询也需登录，但四条报备/签单写链路默认返回 410。
- 地图只按小区聚合展示，不展示具体楼栋、单元、房号、房东电话或看房密码；坐标来源会区分 `verified`、`approximate`、`block-center`。
- 公司、业主、二房东来源由服务端形成唯一互斥分类：公司专用真值或 canonical `source/sourceType/listingType/inventoryType` 中的公司枚举优先；非公司继续按 `ownerType || houseSourceType || source` 的第一个非空字段判定，该字段非法或全部缺失时按既有默认归二房东，派生字段不能提升业主权限。公司专用字段兼容既有 `true/1/yes/y/是/公司/公司房源`，但 `false/0/no` 不得当真；标题、小区名和说明文字不得参与归类。列表、地图、收藏和 Mock 必须同口径，客户端不能通过同名字段改变来源或权限。
- 每次合并部署前必须在目标数据库环境运行只读 `node scripts/listing-source-integrity-audit.js`。它只输出聚合数量；若发现“公司字符串假值 + canonical 公司来源”的旧误固化可疑签名，或数据文件缺失/不可读，退出码 `2` 并停止发布。原始业主/二房东来源被旧迁移覆写后不能凭当前字段安全恢复，必须结合迁移前备份或可靠外部来源人工裁决，禁止按标题或猜测自动改库。

### 2.4 审核与小区库规则

- 服务端小区库是权威来源。命中库的小区视为已匹配；普通中介上传库外小区或在客户端伪称“已匹配”时仍会进入人工审核。
- 编辑房源且小区名未变时，可沿用历史已匹配判定，兼容飞书导入和存量数据。
- 显式申请进入审核任何人可以；显式豁免审核只有管理员生效。
- 业主房源和库外房源的审核状态会影响前台展示，待审核房源不进入前台有效房源和地图。
- 服务端确认的内部员工新建或本人编辑业主/二房东房源时直接落为“已通过 + 待确认”，不进入人工审核；身份只取服务端 `db.users`，客户端伪造角色、上传人或审核字段无效。库外小区仍保留未匹配与待补坐标标记，不能因免审伪造成已匹配或可靠地图坐标；历史待审核记录不会在服务启动时被批量改写。

### 2.5 3/5/7 房态规则

- 第 3 天提醒上传人电话核验房态。
- 第 5 天再次提醒并提升为重点核验。
- 第 7 天未更新固定自动下架，进入后台资产池；失效房源保留在后台，可由管理员恢复。

### 2.6 历史报备到签单到分佣链路（已由第 16 章暂停口径取代）

- 以下仅描述显式恢复模式与历史数据结构，不代表当前小程序存在活动入口。报备保持简单：客户称呼可选，客户手机号必填。
- 签单只能从自己的报备记录发起，不能直接从房源发起。
- 签单只填写成交月租、房东实际支付佣金和可选备注。
- 管理员确认签单后才生成正式分佣记录；公司房源确认后不生成任何抽佣记录。
- 金额统一按分存储，避免小数误差；签单快照会冻结房源、上传人和分佣规则。

### 2.7 需求转化漏斗

- 持久需求兼容保存 `need-funnel-v1` 历史里程碑。M3 起新的敏感查看不再写 L1，报备/签单暂停期不新增 L2/L3；带看仍可在服务端验证本人持久 `needId` 后归因。
- 主指标 `fillL2` 为“有可信报备的需求数 / 持久需求总数”；辅助指标为首次有效推荐 P50/P95、带看率（审核通过带看 / 已报备需求）和成交确认率（已确认 / 已提交）。
- 指标计算会再次核对需求所有人和事件用户，客户端伪造或串绑的 needId 不计；重复事件只保留首次服务端时间。旧客户端或临时需求未携带持久 needId 的带看仍可提交，但不进入漏斗。
- 生产 `ynzy-metric-snapshot.timer` 每日只读写聚合快照，`metric-readout.js` 与 `show-metric-trend.js` 不输出原始 needId、姓名、手机号或地址。
- `/readyz` 会把仍处于待审核且通知三次耗尽的注册申请显示为“注册通知死信 N 条”需处理项；只显示数量，已完成审核的历史申请不计，存在待办时 readyz 返回 503。
- P1.3 已随 `v1-broker@f82f2d7` 于 2026-07-10 完成后端部署：生产 `listings 85 → 85`，`healthz/readyz` 均为 200，漏斗聚合可读且零分母返回 `null`；小程序端带看 `needId` 代码已推送，需随下一次已审整包上传后在客户端生效。

### 2.8 账号密码同步边界

- 后台管理账号和小程序用户仍是两套鉴权记录；只有管理账号保存了服务端 `userId` 绑定时，后台创建/重置该管理账号密码才单向同步到同一小程序用户，并撤销其全部旧小程序会话。旧版本已完成后台改密但绑定用户仍缺密码时，首次输入正确后台密码可在唯一绑定且 scrypt 验证通过后安全回填，无需再次重置。
- 不按管理账号文本或手机号猜测绑定，不自动创建小程序身份。未绑定管理账号只更新后台密码，后台明确提示小程序密码未同步；小程序用户自助改密不会反向修改后台管理密码。
- 所有密码仍只保存 scrypt 哈希，接口和后台列表不返回哈希或明文。

### 2.8A 找房助手推荐房源地图返回边界

- 找房助手推荐卡仍通过底部地图页展示，但进入地图前会保存一份仅驻留当前小程序进程内、且绑定当前登录会话的返回快照；地图顶部只在该入口显示返回箭头，返回后恢复原聊天、推荐卡和需求上下文。快照不写本地持久存储，账号不一致时立即丢弃，且同一快照只允许消费一次。
- 推荐结果已携带明确 `listingIds` 时，这些 ID 是地图展示范围的最终边界。“新天地附近”等位置文字仅用于助手召回，不得再次作为推荐房源自身的 `area/community` 精确筛选条件叠加，否则会把真实的周边推荐全部误筛为空。
- 地图仍只展示服务端允许公开的小区聚合位置与坐标可信度，不新增楼栋、房号、详细地址或其他敏感位置字段；普通底部导航进入地图时不显示找房助手返回箭头。
- 找房助手仍在生成结果时禁止跳转地图，避免销毁在途请求；若加载锚点是临时的 `typing-row`，保存返回快照时改为最后一条真实消息。地图返回按钮有单次在途门，连续点击不会重复压入两个找房助手页面。
- 登录账号切换成功、全局登出或找房助手检测到会话变化时都会清除尚未消费的内存快照。恢复推荐消息时一律把 `feedbackLoading` 归零，避免已被页面切换中断的反馈请求让按钮永久停在加载态。

## 4. 部署形态

### 4.1 服务器路径与服务

- 应用目录：默认 `/opt/ynzy-miniapp`，由 `APP_DIR` 或部署脚本参数覆盖。
- 后端服务：systemd 服务名 `ynzy-miniapp`，配置文件 `deploy/ynzy-miniapp.service`。
- 服务工作目录：`/opt/ynzy-miniapp/server`。
- 启动命令：`node src/index.js`。
- 生产端口：安装脚本会保证服务器 `server/.env` 内 `PORT=3101`，本机探活为 `http://127.0.0.1:3101/healthz`。
- 公网 API 域名：`https://zf-api.ynzyqbot.cn`。

### 4.2 Nginx 配置要点

- 主业务域名 `ynzyqbot.cn` 的兜底仍给企业微信机器人等历史服务，小程序 API 不走主域名兜底。
- 小程序 API 使用独立配置 `deploy/nginx-zf-api-miniapp.conf`，80 端口跳转 HTTPS，443 反代到 `127.0.0.1:3101`。
- WebSocket 实时语音路径必须单独配置：
  - `location = /mini/asr/realtime`
  - `proxy_http_version 1.1`
  - `proxy_set_header Upgrade $http_upgrade`
  - `proxy_set_header Connection "upgrade"`
  - `proxy_read_timeout 3600s`
  - `proxy_buffering off`
- 每次调整后执行 `nginx -t`，再重载或重启 Nginx。

## 22. 2026-07-13 后台审核 HEVC 视频兼容预览

- 问题命中：手机上传的 MP4 可能使用 HEVC/H.265 视频轨，文件与 OSS 签名均正常，但当前 Chrome/Edge 后台审核播放器可能停在 `0:00` 或直接报媒体错误，导致已上传房源视频无法预览审批。
- 服务端新增管理员鉴权接口 `GET /admin/listings/:id/video-compatible-preview`。接口只按数据库中该房源的持久 `videoKey` 生成短期 OSS 读取地址，不接收客户端 URL/Key；持久 Key 仍须满足服务器上传目录前缀、安全路径和 MP4/MOV/M4V 后缀，防止客户端写入任意对象键后把接口当成签名/转码代理。
- SSRF 与权限边界：签名结果只允许 HTTPS、配置中的精确 OSS 主机和精确对象路径，不跟随重定向。Node 完整限长下载后要求实际字节数与 `Content-Length` 精确一致，内容只写入 `0700` 随机目录中的 `0600` 独占临时文件；写入关闭后只读打开并立即删除路径与目录，只把匿名 fd 3 继承给 ffmpeg。ffmpeg 固定 `-protocol_whitelist fd,pipe -fd 3 -f mov -i fd:`，既支持 `moov` 位于文件尾部的普通手机 MP4，又不能自行打开磁盘路径或网络 URL；输出只走 `pipe:1`。输入解码器只允许 HEVC/H.264/AAC，并在解码前限制 4096×4096 像素；子进程关闭 stdin，使用绝对路径、最小无密钥环境和非应用工作目录，Node 为 root 时固定降到非 root UID/GID。OSS 签名、对象 Key、临时路径和 ffmpeg 原始错误均不进入浏览器 URL、参数、环境、日志或错误正文。
- 资源边界：默认最多同时处理 1 路、最长 5 分钟、输出最多 200 MiB，并发名额覆盖完整下载落盘与转码全过程；ffmpeg/Node 双重限制输出，同时限制探测量、流数量、解码/编码/滤镜线程、1920×1080 输出盒、30fps 与码率。成功、源读取/长度核对/写盘失败、客户端断开、超时、spawn 失败、输出越界和正常退出都在返回结论前关闭 fd、移除临时文件并释放并发名额。响应私有、不缓存且明确不支持 Range；页面离开或请求断开会中止 OSS 上游与 ffmpeg。
- 后台审核页先绑定原播放器 `error` 监听再赋源地址；原视频无法播放时自动生成兼容预览，也可手动点击“兼容播放”。兼容响应必须为 `video/mp4`，且播放器触发 `loadedmetadata/canplay` 后才显示成功；Blob 解码失败恢复重试。返回列表、切换任意栏目、会话失效和页面退出都会暂停全部审核播放器、abort 请求并回收 Blob URL；BFCache 返回显示“已释放”并恢复按钮，无 AbortController 时用请求代次隔离迟到成功/失败。新窗口入口只允许 HTTPS（本机开发允许 loopback HTTP）的服务端签名原视频地址。
- 服务器运行依赖为 ffmpeg（须具备 `fd` 协议、`libx264` 与 AAC 编码器）；部署脚本不自动安装/升级。发布前必须在目标服务器以 `mdat` 在前、`moov` 在尾的真实 HEVC+AAC 合成文件，通过与代码一致的 fd 3 参数完成转码，并由 `ffprobe` 确认 H.264/yuv420p + AAC。可选环境项为 `VIDEO_PREVIEW_FFMPEG_PATH`（绝对路径）、`VIDEO_PREVIEW_MAX_CONCURRENT`、`VIDEO_PREVIEW_TIMEOUT_MS`、`VIDEO_PREVIEW_MAX_DURATION_SECONDS`、`VIDEO_PREVIEW_MAX_OUTPUT_MB`、`VIDEO_PREVIEW_UID/GID`。本功能不新增数据库字段或迁移，不信任客户端身份、对象地址或权限字段。

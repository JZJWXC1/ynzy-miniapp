# 交接报告 2026-07-04

## 1. 项目定位与当前架构

一句话定位：寓你住一起第一版是面向内部中介的杭州租房小程序，用公司同步房源与合作房源帮助中介找房、报备、签单并沉淀分佣和留痕。

当前架构：

- 小程序端：微信小程序，底部导航固定为找房、房源、地图、我的；首页含公司房源快照与 `Yooni小助手`。
- Node 后端：`server/src/index.js` 提供 `/mini/*`、`/admin/*`、ASR/LLM、飞书同步、OSS 策略、报备签单等接口。
- JSON 库：运行数据存放在 `server/data/db.json`，由 `server/src/db.js` 读写；生产通过 systemd timer 定时备份。
- OSS：视频上传和读取走阿里云 OSS，后端只保存 `videoKey` 或短期可读 URL，不把视频文件写入 JSON。
- 飞书同步：公司房源从飞书表和素材库同步到本地 `listings`，按房号/楼栋单元房号等 Key 对齐，支持后台立即同步与定时同步。
- LLM 助手：小程序助手和语音链路走后端，游客只匹配公司房源，登录中介可匹配其可见的全部有效房源。
- 管理后台：`admin-web` 使用同一个 Node 服务托管，提供房源、审核、飞书同步、坐标修正、LLM 配置、导出等管理能力。

## 2. 业务规则现行版

### 2.1 分佣矩阵

分佣只由服务端计算，客户端提交的 `brokerId`、`uploaderId`、`commissionRate` 或同名字段不可影响结果。

| 房源情形 | 成交总扣 | 上传人 | 平台 | 分佣记录 |
| --- | ---: | ---: | ---: | --- |
| 公司房源 | 0% | 0% | 0% | 不生成 |
| 二房东房源，普通中介上传 | 20% | 15% | 5% | 管理员确认签单后生成 |
| 业主房源，普通中介上传 | 20% | 20% | 0% | 管理员确认签单后生成 |
| 管理员上传的合作房源 | 20% | 0% | 20% | 管理员确认签单后生成，分佣归平台 |

公司房源详情页文案为“公司房源成交不抽佣，带看中介全佣”；二房东/业主维持 20% 分佣说明。

### 2.2 视频要求

- 公司房源免视频，允许无视频进入公司房源列表和详情；同步素材缺失时后台标记 `missingVideoMaterial=true` 和“缺视频素材”。
- 二房东房源、业主房源必须带真实视频，`videoUrl` 或 `videoKey` 至少有一个。
- 视频本体不写入 `db.json`；OSS 签名播放地址由后端按需生成。

### 2.3 可见性边界

- 游客可看公司房源完整字段：首页快照、列表、详情都公开公司房源完整信息，包括房号、看房方式密码、备注和公司配置的联系方式。
- 游客只能看到公司房源；匿名访问合作房源详情返回 `401` 引导登录。
- 登录中介可看合作房源列表与详情，但合作房源详细地址和房东电话继续走实名、需求单、查看额度和足迹留痕机制。
- 上传、我的、需求单、报备、签单、分佣、足迹、视频上传策略等操作接口强制登录。
- 地图只按小区聚合展示，不展示具体楼栋、单元、房号、房东电话或看房密码；坐标来源会区分 `verified`、`approximate`、`block-center`。

### 2.4 审核与小区库规则

- 服务端小区库是权威来源。命中库的小区视为已匹配；库外小区或客户端伪称“已匹配”的小区会进入人工审核。
- 编辑房源且小区名未变时，可沿用历史已匹配判定，兼容飞书导入和存量数据。
- 显式申请进入审核任何人可以；显式豁免审核只有管理员生效。
- 业主房源和库外房源的审核状态会影响前台展示，待审核房源不进入前台有效房源和地图。

### 2.5 3/5/7 房态规则

- 第 3 天提醒上传人电话核验房态。
- 第 5 天再次提醒并提升为重点核验。
- 第 7 天未更新固定自动下架，进入后台资产池；失效房源保留在后台，可由管理员恢复。

### 2.6 报备到签单到分佣链路

- 报备保持简单：客户称呼可选，客户手机号必填。
- 签单只能从自己的报备记录发起，不能直接从房源发起。
- 签单只填写成交月租、房东实际支付佣金和可选备注。
- 管理员确认签单后才生成正式分佣记录；公司房源确认后不生成任何抽佣记录。
- 金额统一按分存储，避免小数误差；签单快照会冻结房源、上传人和分佣规则。

### 2.7 需求转化漏斗

- 持久需求在 `rentalNeeds[*].funnel` 中只保存 `need-funnel-v1` 固定里程碑时间：首次有效推荐、L1 敏感查看、L2 报备、审核通过带看、L3 成交提交和管理员确认，不保存客户、房源、地址或自由文本。
- 主指标 `fillL2` 为“有可信报备的需求数 / 持久需求总数”；辅助指标为首次有效推荐 P50/P95、带看率（审核通过带看 / 已报备需求）和成交确认率（已确认 / 已提交）。
- 指标计算会再次核对需求所有人和事件用户，客户端伪造或串绑的 needId 不计；重复事件只保留首次服务端时间。旧客户端或临时需求未携带持久 needId 的带看仍可提交，但不进入漏斗。
- 生产 `ynzy-metric-snapshot.timer` 每日只读写聚合快照，`metric-readout.js` 与 `show-metric-trend.js` 不输出原始 needId、姓名、手机号或地址。
- `/readyz` 会把仍处于待审核且通知三次耗尽的注册申请显示为“注册通知死信 N 条”需处理项；只显示数量，已完成审核的历史申请不计，存在待办时 readyz 返回 503。
- P1.3 已随 `v1-broker@f82f2d7` 于 2026-07-10 完成后端部署：生产 `listings 85 → 85`，`healthz/readyz` 均为 200，漏斗聚合可读且零分母返回 `null`；小程序端带看 `needId` 代码已推送，需随下一次已审整包上传后在客户端生效。

### 2.8 账号密码同步边界

- 后台管理账号和小程序用户仍是两套鉴权记录；只有管理账号保存了服务端 `userId` 绑定时，后台创建/重置该管理账号密码才单向同步到同一小程序用户，并撤销其全部旧小程序会话。旧版本已完成后台改密但绑定用户仍缺密码时，首次输入正确后台密码可在唯一绑定且 scrypt 验证通过后安全回填，无需再次重置。
- 不按管理账号文本或手机号猜测绑定，不自动创建小程序身份。未绑定管理账号只更新后台密码，后台明确提示小程序密码未同步；小程序用户自助改密不会反向修改后台管理密码。
- 所有密码仍只保存 scrypt 哈希，接口和后台列表不返回哈希或明文。

## 4. 部署形态

### 4.1 服务器路径与服务

- 应用目录：默认 `/opt/ynzy-miniapp`，由 `APP_DIR` 或部署脚本参数覆盖。
- 后端服务：systemd 服务名 `ynzy-miniapp`，配置文件 `deploy/ynzy-miniapp.service`。
- 服务工作目录：`/opt/ynzy-miniapp/server`。
- 启动命令：`node src/index.js`。
- 生产端口：安装脚本会保证服务器 `server/.env` 内 `PORT=3101`，本机探活为 `http://127.0.0.1:3101/healthz`。
- 公网 API 域名：`https://zf-api.ynzyqbot.cn`。

### 4.2 Nginx 配置要点

- 主业务域名 `ynzyqbot.cn` 的兜底仍给企业微信机器人等历史服务，小程序 API 不走主域名兜底。
- 小程序 API 使用独立配置 `deploy/nginx-zf-api-miniapp.conf`，80 端口跳转 HTTPS，443 反代到 `127.0.0.1:3101`。
- WebSocket 实时语音路径必须单独配置：
  - `location = /mini/asr/realtime`
  - `proxy_http_version 1.1`
  - `proxy_set_header Upgrade $http_upgrade`
  - `proxy_set_header Connection "upgrade"`
  - `proxy_read_timeout 3600s`
  - `proxy_buffering off`
- 每次调整后执行 `nginx -t`，再重载或重启 Nginx。

### 4.3 部署脚本用法

- 本地打包部署包：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package-deploy.ps1
```

- 远程部署脚本：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy-ecs.ps1
```

- `scripts/package-deploy.ps1` 默认不带 `server/.env`、`server/data/`、`server/certs/`。
- `scripts/deploy-ecs.ps1` 会在远端保留 `.env`、`server/data/`、`server/certs/` 和 `lark-*.json`，再替换代码目录并运行 `deploy/install-on-server.sh`。
- 首次种子数据场景才可显式使用 `-IncludeData`，生成包必须按敏感文件管理。

### 4.4 db.json 备份机制

- 定时器：`ynzy-db-backup.timer`。
- 频率：每 30 分钟备份一次。
- 备份服务：`ynzy-db-backup.service`。
- 备份脚本：`deploy/backup-db.sh`。
- 默认数据文件：`/opt/ynzy-miniapp/server/data/db.json`。
- 备份目录：`/opt/ynzy-miniapp-backups/db`。
- 保留份数：最近 48 份。
- 最新备份软链：`/opt/ynzy-miniapp-backups/db/latest.json`。
- `FOOTPRINT_MAX_ROWS` 控制足迹留痕截断上限，生产 systemd 当前设置为 30000。

**异地加密备份（P0-1，2026-07-06 新增，与上面的本地明文备份互补，两层都保留）：**

- 核心库 `server/src/backup.js`；备份 CLI `server/scripts/backup-db.js`；恢复演练 CLI `server/scripts/restore-drill.js`；测试 `server/scripts/backup-restore-v1-test.js`。
- 流程：读源 `db.json` → gzip → AES-256-GCM 加密 → 带时间戳落盘（`db-backup-<UTC>.ygbak`）→ 即时自检 → 异地上传钩子 → 保留清理（默认 30 天）。
- 恢复演练**只读**：解密到系统临时目录，做「六项数量往返一致性校验」（`listings/users/reports/deals/commissionRecords/footprints`，其中 reports/deals 对应库内 `clientReports/dealRecords`），并巡检最近备份是否超 24h；不写回生产。
- 告警：`BACKUP_FAILED/BACKUP_VERIFY_FAILED/BACKUP_EMPTY_SOURCE/BACKUP_REMOTE_REQUIRED/REMOTE_UPLOAD_FAILED/RESTORE_MISMATCH/RESTORE_FAILED/BACKUP_STALE`，均明确报错并非零退出。
- **异地目标生产必填**：默认未配置 `BACKUP_REMOTE_CMD` 即判失败（`BACKUP_REMOTE_REQUIRED`、非零退出），避免「只做本机备份却谎报成功」；本地演练需显式 `BACKUP_ALLOW_LOCAL_ONLY=1` 才允许仅本地成功，生产禁止开启。
- 密钥/异地目标/通知命令只从环境变量读取，仓库不写真实值；本地暂存目录 `server/backups/` 已 gitignore（另加 `*.ygbak` 全局忽略）。详细环境变量、手动操作、cron 配置见 `server/README.md`「异地加密备份（P0-1）」与 `docs/db-json-备份与恢复.md`。
- **待生产落地**：需由用户在服务器配置 `BACKUP_ENCRYPTION_KEY`、`BACKUP_REMOTE_CMD`（异地目标，必填）、可选 `BACKUP_ALERT_CMD`，并加两条 cron（备份 + 恢复演练）。

### 4.5 环境变量清单

只列变量名和用途，不记录任何值。

基础运行：

- `PORT`：后端监听端口；生产为 3101。
- `DATA_FILE`：覆盖 JSON 数据文件路径。
- `NODE_ENV`：运行环境。
- `AUTH_TOKEN_SECRET`：小程序 Bearer token 签名密钥，token 有效期 7 天。

## 一、北极星：双主轴（质量 × 价值），不是单一

对抗校验推翻了"满意率作唯一北极星"：满意率今天 `measurable_today=partial`（生产真值=0，`db.assistantEvalCases` 现 0 条），若唯一北极星线上不可读，团队会去优化评测集而非真实撮合（Goodhart 陷阱）；而且"满意 ≠ 有价值"——中介可对推荐满意却从不解锁/带看/成交。故北极星取**双主轴**：

| 轴 | 指标 | 角色 | 今天可测 | 归属线 |
|---|---|---|---|---|
| **质量轴** | **推荐满意率** | 离线质量准星（门槛制，改动前后对比） | partial（离线合成有、生产真值无） | yooni |
| **价值轴** | **需求填充率-L2（报备）** | 线上只读的价值主轴：需求单里产生可信 needId 报备的占比 | **yes**（每日聚合快照已读出） | shared |

> 为何价值轴选"报备(L2)"而非"查看(L1)"或"成交(L3)"：L1 敏感查看受额度模型（OWNER=3/NORMAL=15）影响，与"是否满足需求"并不完全等价；L3 成交仍较稀疏。L2 报备位于中间、由服务端校验需求归属，最适合作为主指标。带看从 P1.3 起携带持久 needId，只有审核通过才计入辅助带看率。

### P1.3 已落地的在线漏斗契约

- `rentalNeeds[*].funnel` 只固化 `need-funnel-v1` 版本和六个首次服务端时间：有效推荐、L1 敏感查看、L2 报备、审核通过带看、L3 提交、L3 确认；不存客户/房源/自由文本。
- `fillL2` 分母是带服务端 `brokerId` 的持久需求总数；事件必须同时满足 `needId` 存在且事件用户等于需求所有人。重复事件按需求去重，串绑记录不计。
- 首次有效推荐耗时只统计实际返回至少一套房源且结果 trace 绑定同一需求的样本，输出 P50/P95 分钟与样本数。
- 带看率 = 审核通过带看的需求数 / 已报备需求数；成交确认率 = 已确认成交需求数 / 已提交成交需求数。分母为 0 时返回 `null`，不制造 `0/0=0`。
- `metric-readout` 每日快照和 `show-metric-trend` 只输出聚合计数、比例、耗时；原始 needId、用户标识、姓名、手机号和地址不出现在快照或趋势行。

**满意率操作化口径**（拍板后锁定为官方评分标准）：
> 单条满意分 ∈ {0, 0.5, 1}：硬条件（预算/区域/户型/明确硬标签）全中且命中主要软偏好=**1**；硬条件全中但软偏好落空=**0.5**；硬条件有违背/空结果/误报=**0**。满意率 = Σ(满意分)/需求条数。撒谎（把不满足硬条件的房源标进 exact 组）恒判 0 并触发回归门（`assistant-satisfaction-eval-test.js:89-90` `process.exit(1)`）。

## 二、指标树（驱动 → 输入）

因果链：**需求可表达 → 供给完备 → 诚实召回 → 填充率↑ → 满意率↑**。每项标注真实可测性与归属。

### L1 驱动指标（改它们能抬北极星）
| 指标 | 定义 | 可测 | 数据源 | 归属 |
|---|---|---|---|---|
| 需求可表达覆盖率 | 需求里硬+主要软约束被 schema 真实承接（不被静默丢弃）的比例，基线 45%–55% | partial | 白名单 `need-parser.js`(CANONICAL_FEATURES)；解析槽落 `assistantTraceLogs.slots` | yooni |
| 供给数据完备率 | 有效房源中"带真实坐标 且 特征标签非公司默认塌缩"的比例 | **partial**（组成项特征完整率本身 partial，父指标不能更乐观） | 坐标 `domain.js:4044` `coordinateSource`；塌缩审计 MODEL-5 | yooni |
| 诚实近似标注率 | 无 exact 命中轮次里，返回"带差异说明的诚实近似"而非甩回人工的比例（把 0 分转 0.5 分） | partial | 每轮遥测 `assistantTraceLogs.rankingResult.exactCount/nearbyCount` | yooni |
| **需求填充率 L1/L2/L3** | 持久需求产生下游撮合动作（查看/报备/成交，needId + 用户归属交叉验证）的占比——价值主轴本体 | **yes** | `rentalNeeds.funnel` + 足迹/报备/带看/成交兼容回读；每日聚合快照 | shared |

### L2 输入指标（更细的杠杆）
| 指标 | 可测 | 数据源 | 归属 |
|---|---|---|---|
| 坐标可用率（可上图/进半径检索） | partial（`adminListings` 未 surface coordinateSource，须走 `mapPins` 或补导出） | `mapPins`/`domain.js:4044`；无坐标房源在 `match-service.js:1216-1222` 被静默过滤 | yooni |
| 特征标签完整率（非公司默认塌缩） | partial（"塌缩"无可靠只读判定） | 审计 MODEL-5；`isCompanyListing` | yooni |
| 净可检索活跃供给深度 & 新鲜度 | **yes** | `dashboardSummary`(listingCount/staleListingCount/expiredListingCount/areaStats) | **stable/shared** |
| 撮合漏斗逐级转化 C1/C2/C3（查看→带看→成交） | partial（带看无 needId，只能 user+listing 二次 join，会串味） | `footprintRecords`→`showingUploadRows`→`adminDealRows` | shared |
| 需求撮合时长 Time-to-Fill | partial（rentalNeeds/dealRecords 无 dateKey 须解析本地串） | footprints/clientReports 有可靠 dateKey | shared |
| 成交深填率 & 月租 GMV（黄金锚，季度） | partial（dealRecords 稀疏、无 dateKey） | `adminDealRows` `dealMonthlyRentFen` | shared |
| 平台佣金收入（变现主线之一） | partial（`confirmDeal` 生成 `platformCommissionFen`；`commissionRecords` 无 dateKey 须解析） | `commissionRecords.platformCommissionFen` | shared |

> **分佣模型对变现指标的影响（2026-07-08 上线，money 级，可后台配置）**：平台佣金按成交总佣金抽成——业主/二房东**平台默认 10%（后台可配）**、公司房源 **0（带看全佣）**、**自传自带（成交人==上传人）全免且不生成分佣记录**。因此：①「平台佣金收入」= Σ `platformCommissionFen`，**自传自带 / 公司成交贡献 0**——自传自带占比越高，成交上去了平台抽成却不动（读数时要拆分自传自带 vs 跨中介成交）；②改分佣比例只影响新签单、历史记录冻结不变，做趋势时注意口径切换点。守恒双重防线与配置方式见《生产运维手册》§8。

## 三、护栏指标（防撒谎 / 防虚荣 / 防 Goodhart）

前 3 条来自设计，后 4 条为对抗校验补入（缺了它们，满意率可以被"刷"上去）：

1. **零撒谎率**（精确红线）：任一 exact 组出现违背硬条件的房源即记 1 次，全站必须为 0（违则 0 分 + 非零退出回归门）。owning=yooni
2. **敏感信息零外泄**：推荐/回复不得含手机号/房号/经纬度/带签名视频 URL（`safety.js` 常驻回归门，任何提召回改动不得放宽）。owning=shared
3. **不编坐标 / 未知地点不静默全局推**：多候选或坐标不可靠时克制不推、不伪造坐标。owning=yooni
4. **带看审核通过率**（履约真实性/防刷额度）：带看须水印现场照并通过审核；WAF/填充率 L2/L3 须扣未通过带看。owning=admin（`reviewShowingUpload`）
5. **幽灵/陈旧供给率上限**：库存分母中 stale/过期/无坐标/塌缩标签房源占比设上限，防堆陈旧房源做大"供给深度"。owning=shared
6. **【新增】评测集防背题**：满意率评测集须设 holdout、不得用于调参、定期与线上 query 分布比对（防 Goodhart：满意率涨=背题涨）。owning=yooni
7. **【新增】最小样本量 + 置信区间门**：assistantEvalCases 现 0 条、小 N 下满意率%是噪声，达最小 N 与 CI 前不据 delta 决策。owning=yooni
8. **【新增】受控召回 0.5 档封顶**：零撒谎只禁"误标 exact"，不封"近似能差多远"；须给 differenceText 距离/超预算设上限，否则可对离谱房源盖"诚实标注"骗 0.5 分。owning=yooni
9. **【新增】额度触顶 censoring 门**：填充率 L1 受额度上限截断（额度用尽即便满意也无查看）；把"额度触顶率"设为正式护栏并与 fill-rate 读数绑定。owning=shared/stable
10. **助手端点健康**：找房/对话端点请求量、4xx/5xx、P95 维持阈内；降级须返真实本地房源(degraded=true)不返 mock。owning=stable（`request-log.js`）

## 四、可测性现实：一个必须先讲清的跨线约束

对抗校验挖出的关键工程事实（否则"稳定线现在就能建"是空头支票）：

- **domain.js 只导出函数/视图，不导出原始集合**（`module.exports` @ `domain.js:4288-4355`）。稳定线新建脚本 `require('domain.js')` 调用**已导出函数** = 读它的公开 API（合规，等同 health-check.js 调 backup.js），**不是** EDIT domain.js。
- 但导出**视图会丢字段**：`adminListings` 不带 `coordinateSource`、`adminReportRows` 不带 `needId/dateKey`（实测 grep 确认）。这些指标要么走别的导出（如坐标走 `mapPins`），要么**需 yooni 线补一个只读导出**。
- **红线**：稳定线不得直接读 `server/data` 原始 db、不得 EDIT domain.js 加导出。

### 我这条稳定线**现在就能独立只读建**（零跨线依赖）
- 供给侧：净可检索活跃供给深度、新鲜度、区域分布、过期/陈旧计数（`dashboardSummary`）。
- 中介基数与当日活跃：`userCount`/`authedUsers`/`todaySensitiveViews`（`dashboardSummary`）。
- 敏感查看按 needId 归因的填充率 L1（`footprintRecords` 带 needId+action+viewerId，遍历 `adminUsers`）。
- 后台积压护栏：`pendingShowingUploadCount`。
- 端点健康聚合器：扩 `request-log.js` 产出各端点 4xx/5xx/P95（request-log.js 属稳定线本线资产，可 EDIT）——**注意**：现状只逐条 emit `{status,ms}`，P95/分端点错误率**须先建聚合器才能读**。

### 必须 yooni 线先做（稳定线做不了）
- 生产满意率真值：灌 100–200 条真实需求进 `db.assistantEvalCases`（现 0 条）。
- 满意率% 聚合输出：扩 `assistant-satisfaction-eval-test.js`/`eval-runner.js`（assistant* 属 yooni 线）。
- 报备/成交/带看按 needId 的 L2/L3 归因已由 P1.3 完成；生产读出口为每日 `metric-readout` 聚合快照。
- 坐标可用率、特征标签完整率、需求可表达覆盖率（need-parser/坐标库/飞书回填，均 yooni 线）。

## 六、必须你拍板的决策（这几条卡住下一步）

1. **【路线】精确优先 vs 受控召回优先** ——审计里最需要拍板的分叉。
   - 精确优先：无 exact 即诚实返 0 套/追问，绝不推近似（信任无损、体验"甩回人工"）。
   - **受控召回优先（推荐）**：有房但差一点点时主动推近似 + 显式标注放宽了哪一项，把 0 分轮次转 0.5 分；严格挂两道对侧刹车（零撒谎率 + 不编坐标）。
   - 影响：拍板后须**一次性同步改** `eval-runner.js:382`「无房必须返 0 套」断言与满意分 0.5 口径，否则两套评测互判红。

2. **【北极星】接受"满意率 × 需求填充率-报备"双主轴**，还是坚持满意率单轴？（建议双轴：一个离线质量门槛，一个线上价值主轴。）

3. **【投入】needId 归因埋点已执行**：`showingUploads` 与审核通过足迹补可信 needId，需求对象固化首次里程碑；旧客户端缺失 needId 的带看保持兼容但不进入漏斗。

4. **【满意分口径】0/0.5/1 是否锁定为官方评分标准。**

5. **【坐标边界】扩坐标库只补真实坐标，还是允许板块中心兜底？**（审计明确运行时不做兜底；兜底会与"不编坐标"护栏冲突。）
